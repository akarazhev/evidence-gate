# appsec-review: hardening design

- **Дата:** 2026-09-01
- **Статус:** утверждён к планированию
- **Автор ревью:** сессия анализа репозитория от 2026-09-01
- **Следующий шаг:** implementation plan (`writing-plans`)

---

## 1. Контекст

Репозиторий `appsec-review` реализует ручной процесс security-review, где агент
используется как аналитический помощник поверх детерминированных сканеров.
Замысел сильный: продуктом является процедура и её контроли, а не «ИИ ищет баги».

Ревью кода выявило устойчивый разрыв между тем, что утверждает проза, и тем, что
обеспечивает код. Это ровно та ошибка, которую репозиторий учит ловить в чужом
коде: `docs/03-data-handling.md` формулирует принцип «Never rely on an
instruction where you can rely on a refusal», и основные дефекты находятся там,
где сам репозиторий этот принцип нарушает.

Все выводы ревью получены чтением кода, без исполнения. Поэтому первый слой
работ — тесты, фиксирующие текущее поведение: они переводят утверждения ревью из
разряда «прочитано» в разряд «проверено».

## 2. Цели

1. Сделать заявленные контроли настоящими контролями (отказ, а не предупреждение).
2. Устранить случаи, когда инструмент делает необоснованное утверждение о том,
   что было проверено.
3. Закрыть недокументированный канал наружу.
4. Создать тестовый слой, доказывающий, что контроли работают.
5. Сделать идентичность находки устойчивой к правкам кода, чтобы аудит-трейл
   переживал рефакторинг.
6. Дать очередь триажа, пригодную для репозитория с сотнями находок.
7. Записывать решение человека, чтобы у программы появился ground truth.
8. Привести README и доки в соответствие с фактическим состоянием кода.

## 3. Вне области работ

- Реализация `goldenset/run_goldenset.py` (остаётся заглушкой, но честно
  маркируется).
- Реализация `scripts/import_defectdojo.py` (то же).
- Перенумерация файлов в `docs/` — ломает внешние ссылки.
- Любой рефакторинг, не обслуживающий пункты раздела 2.

## 4. Принятые решения

| Решение | Выбор | Обоснование |
|---|---|---|
| Независимость валидатора | Идентификаторы моделей приходят от человека через CLI; совпадение — отказ | Модель ненадёжно идентифицирует сама себя; метрика, стоящая на самоотчёте, недоказуема |
| Egress сканера | Офлайн по умолчанию, сеть — только через явный `SEMGREP_CONFIG` | Тезис «один канал наружу» должен быть правдой из коробки |
| Порядок работ | Характеризационные тесты первыми, слоями по риску | Доказывает, что дефект реален, и даёт исполнителю объективное «готово» |
| Фреймворк тестов | `unittest` из stdlib | Репозиторий гордится тем, что контроль работает без зависимостей; тесты, требующие `pip install`, противоречат этому |

## 5. Язык

Весь код, комментарии, docstring-и, сообщения об ошибках, README и содержимое
`docs/` — **на английском**, как и весь существующий репозиторий. Настоящая
спека и план — на русском, они рабочие документы, а не часть публикуемой
документации.

## Слой 0 — тестовая инфраструктура

**Зачем первым:** `scripts/check_scope.py` — единственный компонент, чей отказ
является контролем безопасности, а не удобством. Всё остальное чинится, опираясь
на него.

### Требования

- Каталог `tests/`, фреймворк `unittest` из стандартной библиотеки.
- Цель `make test` → `python3 -m unittest discover -s tests`.
- Ни сети, ни `semgrep`, ни `pip install` для прогона.
- Фикстуры политики живут в `tests/fixtures/`, а не берутся из живого
  `policy/excluded-paths.yml`. Иначе правка политики ломает тесты и люди
  перестают их запускать.

### Рефакторинг ради тестируемости

`build_packet.build_triage_packet()` (`scripts/build_packet.py:120`) вызывает
`load_policy()` без аргументов и жёстко привязан к реальному файлу политики.
Добавить параметр `exclusions: list[dict] | None = None` — по образцу уже
существующего `check_scope.check_path()`.

### Обязательный тест: проверка порядка

Главное утверждение `docs/03-data-handling.md` — scope-check происходит до
чтения любого содержимого файла (`scripts/build_packet.py:119-126`). Сейчас оно
не проверено ничем.

Тест: политика, в которой целевой файл исключён, при этом файла физически нет на
диске. Ожидается `ScopeViolation`. Если поднимется `FileNotFoundError` — порядок
нарушен, контроль сработал после чтения.

### Покрытие

**`test_check_scope.py`**
- Парсер YAML-подмножества: список `exclusions`, список `scan_noise`,
  комментарии, значения в кавычках, отсутствующий файл политики →
  `FileNotFoundError`.
- Матчинг: `**/.env` ловит `.env`, `a/b/.env`, `./.env`; `.git/` ловит
  `.git/config`; `findings/packets/` ловит вложенное; `**/*.pem` ловит и на
  верхнем уровне, и на глубине.
- Негативные: `src/environment.py` не подпадает под `**/.env`.
- **Регистр:** `.ENV`, `ID_RSA`, `KEY.PEM` — эти тесты изначально красные, они
  ведут фикс в слое 1.
- CLI: exit 0 при разрешённых путях, exit 2 при исключённых, `--list`.

**`test_build_packet.py`**
- Стабильность `finding_id` — полный перечень случаев в §1.5.
- Разбор SARIF, включая `codeFlows` и результаты без `locations`.
- Проверка порядка (см. выше).
- Границы окна в `read_context`: начало файла, конец файла, окно шире файла.

**`test_record_verdict.py`**
- Все пять правил `check_consistency`.
- Матрица `decide_state` по осям severity × verdict × challenge × evidence_level.
- `_fallback_validate`: required, enum, тип, булево против `integer`,
  неизвестное имя типа, элементы массива.

**`test_metrics.py`**
- Пустой лог, `fp_rate` считается только по decided, disagreement rate,
  фильтр `--since`.

### Готовность слоя

Тесты, покрывающие корректное существующее поведение, — зелёные.

Тесты, целящие в известные дефекты (регистр глобов, `decide_state`, накопление
SARIF, `_fallback_validate`), пишутся сразу против **желаемого** поведения и
поэтому красные. Это красная фаза TDD, а не недоделка.

**Не использовать `unittest.expectedFailure`**: после правки в слое 1 такой тест
даёт unexpected success и снова требует правки. Вместо этого исполнитель
сохраняет вывод упавшего прогона — он является доказательством того, что дефект
реален, и требуется разделом «Определение готовности».

Слой 0 покрывает только существующий код. Тесты на новую функциональность слоёв 4
и 5 пишутся внутри этих слоёв по тому же TDD-циклу, а не заранее.

Готовность слоя 0 = инфраструктура работает, зелёные тесты зелёные, список
красных совпадает с перечнем дефектов слоёв 1–3.

## Слой 1 — корректность контролей

Охватывает `record_verdict.py` (§1.1–1.3), `check_scope.py` (§1.4) и
`build_packet.py` (§1.5).

### 1.1 Ложное утверждение в `decide_state`

**Дефект.** При `severity` вне `CHALLENGE_REQUIRED` (то есть `low` или `info`) и
отсутствующем челлендже `challenge_result` становится `None`
(`scripts/record_verdict.py:158-164`), после чего ветка `true_positive`
возвращает rationale `"true positive upheld under adversarial validation"`
(`:182`). Adversarial validation не выполнялась. Строка попадает в
`properties.state_rationale` внутри SARIF и в аудит-лог.

Тот же дефект во второй ветке: `false_positive` при `not needs_challenge`
возвращает `"false positive upheld"` (`:186-187`).

**Правка.** Логика продвижения корректна и не меняется: политика действительно не
требует челленджа для low/info. Меняется формулировка, чтобы она описывала
произошедшее:

- челлендж был и `upheld` → `"true positive upheld under adversarial validation"`
- челленджа не было и он не требуется → `"true positive; severity=<sev> does not
  require adversarial validation under policy"`

Аналогично для `dismissed`.

**Тест.** `decide_state({severity: "low", verdict: "true_positive",
evidence_level: "traced"}, None)` возвращает `("confirmed", <точная ожидаемая
строка>)`. Сверять кортеж целиком точным равенством: проверка на отсутствие
подстроки пропустит любую другую неверную формулировку.

### 1.2 Перезапись `findings/reviewed.sarif`

**Дефект.** `to_sarif()` собирает ровно один `result`, `main()` делает
`write_text` (`:355`). `docs/04-procedures.md`, сценарий 2, предлагает цикл
`for f in findings/verdicts/audit-*.json; do record_verdict.py --verdict "$f"; done`.
Переживает только последняя находка. Это подрывает критерий graduation
«reviewed SARIF imported into the findings store».

**Правка.** Накопление:

1. Если `reviewed.sarif` существует — прочитать, взять `runs[0].results`.
2. Заменить результат с совпадающим `properties.finding_id`, иначе дописать.
3. Отсортировать по `finding_id` — файл должен быть диффабельным.
4. Записать обратно.

Битый или нечитаемый существующий файл — громкий отказ с non-zero, а не молчаливая
перезапись. Флаг `--fresh` для осознанного старта с нуля.

**Тесты.** Две записи подряд дают два результата; повторная запись того же
`finding_id` заменяет, а не дублирует; порядок детерминирован; битый файл даёт
отказ; `--fresh` очищает.

### 1.3 Дыры в `_fallback_validate`

`scripts/record_verdict.py:71`. Существует, чтобы отсутствие `jsonschema`
деградировало проверку, а не отключало её. Сейчас деградация сильнее заявленной:

- `isinstance(True, int)` истинно в Python, поэтому булево проходит как `integer`.
  Нужен явный отказ.
- Элементы массивов не проверяются вообще: без `jsonschema` содержимое
  `data_flow` и `refutation_attempts` не валидируется. Реализовать обход
  `items`.
- `py[name_]` даёт `KeyError` на незнакомом имени типа. Нужен `ValidationError`.

Полный draft-07 не реализуется — это осознанное ограничение, зафиксировать в
docstring.

**Тест против дрейфа схемы.** Схема содержит две конструкции `allOf`, которые
fallback-валидатор не покрывает и которые компенсирует `check_consistency`.
Написать тест, читающий `templates/verdict.schema.json`, извлекающий условия
`allOf` и проверяющий, что для каждого есть соответствующее правило в
`check_consistency`. Разъедутся — упадёт тест.

### 1.4 Регистр глобов в `check_scope`

**Дефект.** `fnmatch.fnmatch` (`scripts/check_scope.py:117`) применяет
`os.path.normcase`, который на POSIX является тождеством. На macOS с APFS по
умолчанию файловая система регистронезависима, поэтому `.ENV`, `ID_RSA`,
`KEY.PEM` — те же самые файлы с тем же содержимым, но под паттерны `**/.env`,
`**/id_rsa`, `**/*.pem` не подпадают.

**Правка.** Сравнение приводить к нижнему регистру с обеих сторон, используя
`fnmatch.fnmatchcase` для предсказуемости на всех платформах. Регистрозависимость
глобов не должна зависеть от ОС.

**Правка политики.** Добавить в `policy/excluded-paths.yml` паттерн `**/.envrc`
(direnv, типовое место для секретов) — сейчас не покрыт.

### 1.5 Нестабильный `finding_id`

**Дефект.** `scripts/build_packet.py:32-35` считает
`sha256(f"{rule_id}:{file_path}:{line}")`, а docstring утверждает «Stable ID so
the same finding keeps its identity across rescans». Для живого репозитория это
неправда: правка выше по файлу сдвигает строку, id меняется, находка теряет всю
историю вердиктов. SARIF-подавление для `dismissed` привязано к тому же id,
поэтому отклонённая как false positive находка воскресает после первого же
рефакторинга и триажится заново.

По последствиям это крупнее прочих дефектов: остальные искажают отдельные
утверждения, этот разрушает аудит-трейл во времени.

**Правка. Порядок источников идентичности:**

1. Фингерпринт сканера, если он есть в SARIF: `result.partialFingerprints` либо
   `result.fingerprints`. SARIF 2.1.0 определяет их ровно для этой задачи.
   Выбор ключа детерминирован: фиксированный список предпочтений, при промахе —
   первый ключ в лексикографическом порядке.
2. Иначе — по содержимому:
   `sha256(rule_id + ":" + file_path + ":" + normalized_snippet + ":" + occurrence_index)`.

`normalized_snippet` — текст флагнутого региона, у каждой строки срезаны ведущие
и хвостовые пробелы, пустые строки удалены. `occurrence_index` — порядковый номер
этого нормализованного фрагмента среди одинаковых в том же файле, с нуля. Без
него повторяющиеся одинаковые фрагменты в одном файле схлопнутся в единый id.

Идентичность ломается при перестановке одинаковых фрагментов местами. Случай
редкий, цена приемлема — зафиксировать в docstring, а не умалчивать.

**Docstring.** Текущий лжёт. Переписать так, чтобы он описывал реальную гарантию:
устойчивость к сдвигу строк и неустойчивость к изменению самого фрагмента.
Вторая — не дефект, а желаемое поведение: изменённый код обязан пересматриваться.

**Смена схемы идентичности ломающая.** Ввести поле `id_scheme` со значением
`content-v1`.

**Разделение по слоям.** Слой 1 вводит константу и кладёт поле в пакет — это всё,
что живёт в `build_packet.py`. Слой 2 доводит её до `properties` результата SARIF
и до колонки в `triage-log.csv`, и там же добавляет отказ при встрече строк с
иной схемой. И то, и другое находится в `record_verdict.py` и опирается на тот же
механизм, что и сверка заголовка `LOG_FIELDS`; разносить их по слоям значило бы
строить его дважды. Между слоями 1 и 2 SARIF временно остаётся без поля — это
переходное состояние внутри одного потока работ, а не поставляемое.
В сообщении об отказе — инструкция заархивировать прежний `findings/` либо
перетриажить.

**Тесты.**
- Вставка строки в начало файла-фикстуры не меняет id.
- Изменение самого фрагмента меняет id.
- Два одинаковых фрагмента в одном файле дают разные id.
- Фингерпринт сканера имеет приоритет над содержимым, выбор ключа детерминирован.
- Отсутствующий регион или пустой фрагмент дают внятную ошибку, а не хеш пустоты.

## Слой 2 — контракт независимости

### Дефект

`scripts/record_verdict.py:315` при совпадении моделей триажа и валидации только
печатает WARNING. Хуже: `reviewer.agent` заполняет сама модель в своём JSON, а
модели ненадёжны в самоидентификации. Метрика №4 из `scripts/metrics.py`,
объявленная решающей для оценки программы, стоит на самозаявленном поле.

`docs/04-procedures.md` называет независимость механизмом: «a second pass without
it is theatre». Механизм, обеспеченный предупреждением, — не механизм.

### Требования

- `record_verdict.py` получает обязательный `--agent`. `--validator` обязателен
  тогда и только тогда, когда передан `--challenge`. Обе половины этого «тогда и
  только тогда» — отказы: `--validator` без `--challenge` записал бы валидатора,
  который ничего не валидировал.

**Челлендж привязывается к конкретной ревизии вердикта.** Привязки по
`finding_id` недостаточно: челлендж, подтвердивший true_positive, принимался при
замещении вердикта на false_positive, то есть авторизовал противоположное
утверждение. Схема челленджа получает обязательное поле `verdict_digest` —
канонический хеш вердикта, для которого челлендж строился. `build_packet`
кладёт его в пакет челленджа, модель копирует дословно, `record_verdict`
пересчитывает хеш переданного вердикта и отказывает при несовпадении. Модель
может ошибиться при копировании, и тогда исход — отказ, а не тихое принятие.
- Сравнение выполняется по значениям от человека.
- Совпадение — отказ с non-zero и **без единой записи**: ни в
  `triage-log.csv`, ни в `reviewed.sarif`. Наполовину записанный результат хуже
  отсутствующего.
- Поля `reviewer.agent` и `validator.agent` из JSON модели сохраняются, но
  записываются в лог как `agent_self_reported` и `validator_self_reported`.
  Расхождение с CLI — предупреждение, не блокировка: авторитет у человека, а само
  расхождение является полезным сигналом.

### Миграция лога

`LOG_FIELDS` (`scripts/record_verdict.py:38-43`) растёт на три колонки:
`agent_self_reported`, `validator_self_reported` и `id_scheme` (последняя — из
§1.5).
Слой 5 добавит ещё пять (`human_decision`, `human_decision_at`,
`human_decision_by`, `human_rationale`, `supersedes`), поэтому механизм сверки
строится один раз здесь и переиспользуется, а не пишется заново.

Дописывание в существующий файл через `csv.DictWriter` с новым набором полей
молча разъедет строки. Требование: сверять заголовок существующего файла с
`LOG_FIELDS` и при несовпадении отказываться с инструкцией по миграции.

### Сопутствующие изменения

- `templates/verdict.schema.json` и `templates/challenge.schema.json`: обновить
  `description` у `agent` — «self-reported by the model; not authoritative,
  see docs/04». Обязательные поля не меняются, ломающего изменения нет.
- `scripts/metrics.py:85-88`: `same_model_validations` считать по авторитетным
  колонкам. После этой правки значение всегда 0 для новых записей; оставить как
  индикатор для строк, записанных до изменения.
- `Makefile`: цель `record` получает `AGENT=` и `VALIDATOR=` с внятной ошибкой
  при отсутствии.
- `docs/04-procedures.md` и `prompts/adversarial-validate.md`: обновить примеры
  команд.

## Слой 3 — egress

### Дефект

`docs/03-data-handling.md` заявляет: «In manual mode there is exactly one path
out: the review packet an engineer builds and submits.» При этом
`scripts/scan.sh:7` выполняет `semgrep scan --config auto`, который обращается к
реестру semgrep.dev за правилами и по умолчанию отправляет телеметрию. Это второй
канал наружу, не задокументированный и не покрытый `check_scope.py`.

### Требования

- `--metrics=off` безусловно, во всех режимах.
- Источник правил по умолчанию — локальный каталог `rules/` в репозитории.
- Пустой или отсутствующий `rules/` — отказ с внятным сообщением. **Проверка
  выполняется до вызова semgrep**, чтобы путь отказа был тестируем на машине без
  установленного semgrep.
- Выход в реестр — только через явный `SEMGREP_CONFIG=p/security-audit`. В этом
  случае скрипт печатает баннер: это второй канал наружу, ссылка на `docs/03`.
- Использованный конфиг всегда печатается в вывод прогона.

### Артефакты

- Каталог `rules/` с `README.md`, объясняющим, что набор правил заполняется под
  конкретный репозиторий, и как это сделать.
- `docs/03-data-handling.md`: новый подраздел «The scanner is also a channel» —
  честный учёт и описание того, как офлайн-режим по умолчанию его закрывает.

### Тест

`tests/test_scan_sh.py`: запуск `scan.sh` с пустым `rules/` во временном каталоге
даёт non-zero и сообщение об отказе; semgrep при этом не требуется. Статическая
проверка наличия `--metrics=off` в скрипте.

## Слой 4 — очередь триажа

**Зачем.** `make list` печатает все находки подряд, `make triage N=` берёт одну по
индексу. На реальном репозитории semgrep выдаёт сотни результатов. Процесс
упирается в это не по корректности, а по объёму: нет способа спросить «покажи
только непроверенное» или «только error».

**Ограничение, которое легко нарушить.** На момент `list` вердикта ещё нет,
поэтому политическая `severity` и `priority_class` неизвестны — их присваивает
агент позже. Фильтровать можно только по тому, что реально есть в SARIF: `level`,
`ruleId`, путь. **Не изобретать здесь маппинг SARIF `level` → политическая
severity**: это разные шкалы, и их смешение породит ложную уверенность ровно того
рода, который весь репозиторий призван предотвращать.

**Фильтры `build_packet.py --list`:**

| Флаг | Поведение |
|---|---|
| `--level error,warning` | По SARIF `level`, список через запятую |
| `--rule <substring>` | Подстрока в `ruleId` |
| `--path <glob>` | Глоб по пути файла, тем же матчером, что и `check_scope._matches` |
| `--unreviewed` | Только находки, для которых нет `findings/verdicts/<id>.json` |
| `--limit N` | Первые N после сортировки |
| `--json` | Машинный вывод, по образцу `metrics.py --json` |

`--unreviewed` — главный по ценности: на повторном скане нужна только новая
работа. Он опирается на стабильный `finding_id` из §1.5 и без него бесполезен;
порядок слоёв это учитывает.

**Сортировка детерминирована:** `level` (error → warning → note), затем путь,
затем строка.

**Идентификация по id.** Индексы зависят от применённых фильтров, поэтому
`make triage N=7` перестаёт быть воспроизводимым. Добавить
`build_packet.py --finding-id F-abc` и `make triage ID=F-abc`. Индекс остаётся
для интерактивной работы, id — для скриптов, тикетов и воспроизводимости.
В шапке вывода `--list` печатать, что индексы относятся к отфильтрованному
списку.

**Сводка** в конце вывода: всего находок, из них уже с вердиктом, показано после
фильтров.

**Makefile:** `make list LEVEL=error UNREVIEWED=1`, `make triage ID=F-abc`.

**Тесты.** Каждый фильтр на фикстурном SARIF; комбинация фильтров; `--unreviewed`
против фикстурного каталога вердиктов; детерминированность сортировки; форма
`--json`; `--finding-id` с несуществующим id даёт внятную ошибку и non-zero.

## Слой 5 — решение человека и пересмотр вердиктов

**Зачем.** `CLAUDE.md` открывается утверждением: каждый вердикт есть рекомендация,
которую человек принимает, отвергает или эскалирует. Ни в схеме, ни в логе, ни в
CLI нет места, куда это решение записывается. Состояние `human_review` фиксирует,
что человек нужен, но не то, что он решил.

Без этого `false_positive_rate` измеряет не точность агента, а долю находок,
которые конвейер отклонил. Пилот проводится ровно затем, чтобы ответить «стоит ли
это продолжать», и величины, отвечающей на этот вопрос, в репозитории нет.

### 5.1 Запись решения человека

Отдельный скрипт `scripts/record_human_decision.py`, не флаг к рекордеру: решение
принимается позже записи вердикта, часто другим человеком и в другой день.

```
record_human_decision.py --finding-id F-abc --decision rejected \
                         --by <роль или хэндл> --rationale "..." [--minutes N]
```

- `--decision`: `accepted` | `rejected` | `escalated`.
- Предмет согласия — **итоговое состояние конвейера** (`final_state`), а не
  исходный вердикт агента. Зафиксировать это в справке и в `docs/04`: иначе два
  человека будут понимать поле по-разному, и величина станет бессмысленной.
- Отказ с non-zero, если вердикта для этого `finding_id` в логе нет.
- Дописывает строку в `triage-log.csv` и обновляет `properties` соответствующего
  результата в `reviewed.sarif`.

**JSON-схемы для этого нет и не должно быть.** Схемы в `templates/` существуют как
контракт вывода модели. Решение человека вводится человеком через CLI, поэтому
валидируется argparse-ом и enum-ом, а не схемой. Зафиксировать в `docs/03`, чтобы
никто не «дополнил» набор схем из соображений симметрии.

**Не писать сюда персональные данные.** `--by` — роль или рабочий хэндл;
`triage-log.csv` коммитится (`docs/03`), и почта или ФИО в нём станут постоянной
частью истории репозитория. Проверку не автоматизируем, но требование выносим в
справку скрипта и в чек-лист `docs/03`.

### 5.2 Пересмотр вердикта

Повторная запись того же `finding_id` сейчас молча дописывает вторую строку.
Требование: `record_verdict.py` отказывается, если вердикт для этого id уже есть,
пока не передан `--supersede`. Сообщение об отказе называет дату существующей
записи.

Лог остаётся **append-only**: аудит-трейл не переписывается, новая строка несёт
`supersedes` со ссылкой на `reviewed_at` предыдущей. SARIF, наоборот, отражает
текущее состояние и заменяет результат по `finding_id` — это уже сделано в §1.2.
Разные артефакты, разные гарантии, и обе намеренные.

### 5.3 Метрики считают находки, а не строки

**Дефект, вносимый этой спекой.** После §1.2 SARIF заменяет результат по
`finding_id`, тогда как лог дописывает. `metrics.compute` считает строки, поэтому
пересмотренная находка учитывается дважды и числа двух артефактов расходятся.
Дефект вносит слой 1, чинится он здесь — раньше чинить нечего.

Правка: `metrics.py` схлопывает строки по `finding_id`. Число пересмотров
выводится собственной величиной — оно само по себе интересно.

**Два типа строк, два правила слияния.** Строка вердикта **замещает** вердикт
целиком, вместе с пустыми полями: перетриаж без челленджа не должен наследовать
`challenge_result` и `validator` от прежнего прогона, иначе лог утверждает
второй проход, которого не было. Строка решения человека **накладывается** на
действующий вердикт, меняя только поля решения.

**Очерёдность определяет момент записи, а не `reviewed_at`.** Первая редакция
предписывала пару `(reviewed_at, индекс)`. Это неверно по той же причине, по
которой `--agent` переехал в CLI: `reviewed_at` заполняет модель в своём JSON,
то есть это самоотчёт, а на самоотчёт нельзя опирать управляющее решение. При
несовпадении писатель и метрики расходились — SARIF замещает по порядку записи,
метрики сортировали по заявленному времени, и находка могла числиться dismissed
в одном артефакте и confirmed в другом.

Рекордер проставляет собственную колонку `recorded_at` — UTC, момент записи. Она
и есть ключ очерёдности и супersession, вместе с позицией строки для ничьих.
`reviewed_at` сохраняется как факт («модель утверждает, что смотрела тогда-то»),
но ничем не управляет. `--since` тоже считает по `recorded_at`: вопрос «что
происходило в этом окне» — про работу программы, а не про заявления моделей.

**`--since` фильтрует находки, а не строки, и применяется после схлопывания.**
Отсев строк до схлопывания оставляет свежую строку решения без её вердикта, и
находка попадает в метрики без состояния, уровня доказательности и времени.
Критерий — время последнего события находки: если оно в окне, находка входит
целиком, со всей своей историей.

**Время инженера разделяется по видам.** Минуты строк вердикта суммируются в
`triage_minutes_total`: перетриаж действительно стоил этого времени, и метрика
№1 обязана это показывать. Минуты решений человека идут отдельной величиной —
это другая работа, и складывать её с триажом значило бы переименовать метрику,
не сказав об этом.

### 5.4 Метрика согласия человека

Новый блок вывода «AGENT ACCURACY (ground truth)»:

- Покрытие: у скольких из decided находок есть решение человека.
- Разбивка accepted / rejected / escalated.
- Точность агента = `accepted / (accepted + rejected)`.
- Предупреждение при низком покрытии: величина посчитана на смещённой выборке,
  доверять ей нельзя. Тот же приём, что и существующее предупреждение о нулевом
  disagreement rate.

**Когда знаменатель не определён, ставки не печатаются.** Если decided равно
нулю, покрытие неопределимо, и точность в этом случае не выводится — даже если
решения записаны, например на находках в состоянии `human_review`. Счётчики
accepted / rejected / escalated печатаются всегда, потому что это факты;
производные доли — только когда есть от чего их считать. Это то же правило, что
и evidence_level: сообщать установленное, воздерживаться от остального.

**Переименование существующей величины.** `false_positive_rate_pct` называет
себя точностью, а измеряет долю отклонений конвейером. Переименовать в
`dismissal_rate_pct` и в выводе `render()` подписать честно. Точность агента —
это новый блок, и смешивать их нельзя.

### 5.5 Критерии выхода из пилота

`docs/07-graduation.md` требует прохождения golden set, а раннер остаётся
заглушкой (раздел 3). Значит пилот формально не может завершиться успехом.

Решение: ввести отдельный набор pilot exit criteria — список graduation минус
golden set, плюс покрытие решениями человека и точность агента из §5.4.

**Порог покрытия и порог точности назначаются до старта пилота, а не после.**
Числа выбирает владелец программы; спека фиксирует только требование, что они
записаны заранее. Иначе разбор результатов превратится в подгонку критериев под
полученные цифры.

### Тесты

- `record_human_decision` отказывается на неизвестном `finding_id`.
- Недопустимое значение `--decision` отвергается.
- Строка появляется в логе, `properties` в SARIF обновляются.
- `record_verdict` отказывается на дубликате без `--supersede` и принимает с ним.
- `metrics` схлопывает по `finding_id`: пересмотренная находка считается один раз.
- Точность считается только по строкам с решением человека.
- Предупреждение о низком покрытии срабатывает.

## Определение готовности

- `make test` зелёный на голом Python 3.9+ без единой установки.
- У каждого дефекта из слоёв 1–3 и §5.3 есть тест, который **падал до** правки и
  **проходит после**. Исполнитель обязан продемонстрировать оба состояния, а не
  только зелёное.
- `make check-scope`, `make list` на фикстурном SARIF и `make metrics` на пустом
  логе продолжают работать.
- В тестовом наборе нет обращений к сети.
- Тест демонстрирует: вставка строки в начало файла не меняет `finding_id`.
- `make list UNREVIEWED=1` на фикстуре возвращает только находки без вердиктов.
- Пересмотренная находка учитывается в `metrics` один раз, а не дважды.
- `record_verdict` на дубликате без `--supersede` отказывает.
- `grep -r '<' CLAUDE.md` в разделах-плейсхолдерах либо чист, либо
  `make check-template` честно падает — оба состояния допустимы, но должны быть
  согласованы.
